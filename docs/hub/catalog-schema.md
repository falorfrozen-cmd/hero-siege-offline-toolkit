# Catalog schema

`catalog/catalog.json` is the Toolkit Hub's only source of truth about what the
tools are, where their artifacts live, and what each one needs in order to
run. It is generated by [`tools/build_catalog.py`](../../tools/build_catalog.py)
from the hand-written rules in
[`catalog/sources.toml`](../../catalog/sources.toml), signed with minisign, and
fetched by the hub as a single request.

Why generated and signed rather than queried live: **The verification chain** in
[`docs/hub/design.md`](design.md). The short version is that a live query to ten
GitHub APIs has nothing to sign — the hub would be trusting whatever the network
handed it, one request at a time, with no way to tell a swapped asset from a new
release.

---

## Files

| File | Committed | What it is |
| --- | --- | --- |
| `catalog/sources.toml` | yes | The per-tool rules a human maintains. |
| `catalog/catalog.json` | yes | The generated catalog. Also embedded in the hub as its offline fallback. |
| `catalog/catalog.json.minisig` | yes | Detached minisign signature over the exact bytes of `catalog.json`. |
| `catalog/catalog-signing.pub` | yes | The public key the hub verifies against. Embedded at compile time. |
| the matching secret key | **no** | Lives outside the repository; in CI it is the `HUB_MINISIGN_SECRET_KEY` secret. |

## `catalog.json`

```jsonc
{
  "schema": 1,
  "generated": "2026-09-11T21:53:52Z",
  "tools": [ /* one object per tool, in sources.toml order */ ],
  "warnings": []
}
```

`generated` is UTC, second precision. `warnings` carries non-fatal notes from the
build (for example a checksum sidecar that could not be read); anything actually
wrong is a build failure, not a warning.

### Tool object

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | Stable, lowercase, hyphenated. Used as the install directory name and as the key in `state.json`. **Never change it** — renaming an id orphans an installed copy. |
| `name` | string | What the card shows. |
| `summary` | string | One line, under about 70 characters. |
| `repo` | string | `owner/name` on GitHub. |
| `submodule` | string | Optional path of the submodule for developer mode. Empty for release-only integrations such as Codex. |
| `version` | string | **From the git tag**, `v` stripped. See "Version comes from the tag" below. |
| `tag` | string | The tag verbatim, for building release URLs. |
| `published` | string | The release's `published_at`, ISO-8601 UTC. |
| `license` | string | SPDX id, or `NOASSERTION` where the repository carries no licence file. |
| `requires` | object | See below. |
| `artifact` | object | See below. |
| `launch` | object | See below. |
| `source_launch` | object? | Present only when the submodule can be run from source. |
| `notes_url` | string | The release page. |
| `notes` | string | The release body, truncated at 8000 characters. Carried so the detail view has a changelog offline. |
| `guide` | string | Repo-relative guide path, under `docs/submodules/` or `docs/tools/` for release-only integrations. |

### `requires`

| Field | Meaning |
| --- | --- |
| `admin` | Needs Administrator (`SeDebugPrivilege`). The hub itself runs non-elevated and elevates this tool per launch. |
| `game_closed` | Must not run while `Hero_Siege.exe` is up. Save editors, mainly. |
| `game_running` | The opposite: needs a live `Hero_Siege.exe` to attach to. The memory tools. |
| `windows_only` | False only for the Steam Deck editor, which is a browser page. |

`admin` and `launch.elevate` must agree; a test enforces it.

### `artifact`

| Field | Meaning |
| --- | --- |
| `kind` | `zip`, `exe`, `nsis` or `html`. See "Kinds". |
| `name` | The release asset's filename, exactly as GitHub serves it. |
| `url` | `browser_download_url`. |
| `size` | Bytes, from the release metadata. |
| `sha256` | Lowercase hex. The hub refuses any download that does not match. |
| `sha256_source` | `computed`, `published`, or `published+verified` — see below. |
| `strip_prefix` | For archives: the single wrapping directory to remove on extract, or `""`. **Derived by reading the archive**, not declared. |
| `install_as` | For `exe`/`nsis` only: the filename to save the download under, so the launch path stays stable across versions. |

`sha256_source` records how the hash was arrived at:

- `published+verified` — the release ships a checksum sidecar **and** the bytes we
  downloaded hash to the same value. This is the normal case and the strongest one.
- `computed` — no sidecar; the generator downloaded and hashed the asset itself.
- `published` — `--no-download` was used, so the sidecar was trusted without
  re-hashing. Acceptable for a quick local run, not for a published catalog.

A sidecar that *disagrees* with the bytes is a hard failure. The generator refuses
to pin either value, because one of the two is lying and picking a winner
silently is how a bad artifact gets a good-looking hash.

### `launch`

| Field | Meaning |
| --- | --- |
| `exe` | Path to the entry point, relative to the install directory (after `strip_prefix` comes off). For `kind: "html"` this is the document to open. |
| `args` | Argument vector. |
| `elevate` | Spawn through `ShellExecuteW`'s `runas` verb. |
| `ports` | Loopback ports the tool may bind. Used to notice an instance already running outside the hub. |
| `health` | Optional. `{ url, timeout_s, any_status? }`. |

`health.any_status` exists for HS Offline Launcher, which binds a per-process HMAC
token and answers an unauthenticated probe with 401/403. Any HTTP status proves
the server is listening, which is the only thing the hub is asking.

Tools with no HTTP surface — the two Tkinter apps, the memory scanners — have no
`health` block, and the hub falls back to "the process is still alive".

### Kinds

| Kind | Arrives as | Installed by | Launched by |
| --- | --- | --- | --- |
| `zip` | A zip archive | Extract, minus `strip_prefix` | Spawning `launch.exe` |
| `exe` | A single executable | Saving it as `install_as` | Spawning `launch.exe` |
| `nsis` | An installer executable | Not installed by the hub | n/a — the hub links to it |
| `html` | A zip around a web page | Extract, minus `strip_prefix` | Opening `launch.exe` in the browser |

`html` describes how the hub *opens* the tool, not how it arrives: the Steam Deck
editor ships as a zip and extracts exactly like `zip` does.

## `sources.toml`

Same shape, minus everything the generator resolves. The fields a maintainer
writes are `id`, `name`, `summary`, `repo`, `submodule`, `license`, `guide`,
`asset_pattern`, `kind`, `[tool.requires]`, `[tool.launch]`,
`[tool.launch.health]` and `[tool.source_launch]`.

`asset_pattern` is a Python regex, anchored at both ends, applied to the asset
filename. It must match **exactly one** asset: zero matches and several matches
are both fatal. That strictness is the point — HSCraftSim's latest release ships
seven assets and hs-stat-forge three, so "the artifact" is a choice somebody has
to make on purpose.

`strip_prefix` may be declared to override the derived value; leave it out unless
you are running with `--no-download`.

### Version comes from the tag

HS-ValueEditor's tag `v1.0.2` ships an asset called
`HSValueScanner-Windows-v1.0.1.zip`. If the catalog read the version out of the
filename it would publish 1.0.1 against a release that is permanently v1.0.2, and
the hub would offer the same update forever: installed 1.0.1, available 1.0.1,
newer tag never arriving. The tag wins, always.

## Running the generator

```bash
py -3 tools/build_catalog.py
```

Downloads every artifact to hash it (about 210 MB across the ten tools) and
writes `catalog/catalog.json`.

```bash
py -3 tools/build_catalog.py --only forgepact hscraftsim --cache-dir .cache
```

Rebuild two tools, keeping the downloads for the next run.

```bash
py -3 tools/build_catalog.py --no-download
```

Trust the releases' own checksum sidecars. Fast, but it cannot derive
`strip_prefix` or check that `launch.exe` is really in the archive, so it is for
local iteration rather than for publishing.

```bash
py -3 tools/build_catalog.py --sign --key "%LOCALAPPDATA%\Hero Siege Toolkit\catalog-signing.key"
```

Also writes `catalog/catalog.json.minisig`.

Unauthenticated GitHub allows 60 requests an hour and a full build spends about
thirty. Pass `--token` (or set `GITHUB_TOKEN`) when iterating.

## Signing

```bash
py -3 tools/minisign.py keygen \
    --secret-key "%LOCALAPPDATA%\Hero Siege Toolkit\catalog-signing.key" \
    --public-key catalog/catalog-signing.pub
py -3 tools/minisign.py export-seed --key "%LOCALAPPDATA%\Hero Siege Toolkit\catalog-signing.key"
```

The second command prints the value for the `HUB_MINISIGN_SECRET_KEY` repository
secret. It is deliberately a separate command rather than something `keygen`
prints, because a key echoed into a terminal is a key in that terminal's
scrollback.

Signatures are minisign's prehashed variant (`ED`): Ed25519 over BLAKE2b-512 of
the file. The hub verifies with the `minisign-verify` crate, and
[`tools/minisign.py`](../../tools/minisign.py) implements the same format in pure
standard library so the generator needs no pip install.

Verification checks **both** signatures in the file — the one over the content and
the one over `signature || trusted comment`. Checking only the first and then
displaying the trusted comment is the standard minisign misuse, and
`tests/test_minisign.py` has a test that fails if we ever regress to it.

## Changing the schema

`schema` is an integer, currently `1`. Bump it for any change that an older hub
would misread, and leave it alone for additive fields an older hub will ignore.
The generator refuses to run against a `sources.toml` whose `schema` it does not
recognise, so the two halves cannot drift apart unnoticed.
